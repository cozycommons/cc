# Crowdset implementation

## Architecture
Retain the separate FastAPI package and optional Python environment, local loopback port 8010, and `/crowdset` React route. Hosted mode uses a separate Docker application on the existing HTTPS origin, existing Supabase Auth identity and authenticated shared-set JSON metadata with uploader ownership. No shared backend initialization, database or migration changes.

## Admin authorization

Read `app_metadata.crowdset_admin === true` from the existing live Supabase `/auth/v1/user` verification on every authenticated request. Never accept roles from user-editable metadata, request bodies, headers, or a client-decoded JWT. Missing, false, or nonboolean flags grant no admin rights; revocation takes effect on the next request without waiting for token refresh. Operators grant/revoke this Crowdset-specific flag through trusted Supabase administration, preserving other app metadata. No role-management endpoint is exposed to users.

Only admins can delete a set. Admins can remove any clip; other users can remove only clips with their verified uploader ID. Return independent `can_delete` flags for sets and clips, and enforce the same rules on canonical and legacy API paths. `can_manage`/`can_edit` still control existing soundtrack/exclusion behavior and do not grant deletion rights. Admin visibility includes owned private sets, but never ownerless local data. Local loopback mode retains standalone control. Clip removal keeps the existing soft-delete and storage-reclamation behavior. Set deletion retains its existing confirmation and full cleanup.

## Processing and publication
- New sets carry schema version 2; normal uploads use the recording role. Existing crowd roles are compatible ordinary contributions. Legacy reference roles remain excluded, preserving the old explicit timing-only contract without deleting media.
- Decode included ordinary uploads to bounded 32 kHz mono float WAVs. Preserve peaks above full scale until gained PCM quantization. Measure finite samples, energy, clipping fraction, near-silent one-second blocks, and loudness to determine usable sources. Choose longest duration, then fewer clipped samples, fewer silent blocks, stable UUID. Quality has no influence across different durations.
- Analyze the chosen source with the existing spectral-change features. Give it offset zero and match other sources to it with existing conservative multiwindow checks. There is no graph solver. Very short clips cannot match another source but can be the sole usable source.
- Plan union bounds from all included matches; shift offsets by the earliest start, keeping original anchor-relative origin in metadata. Keep all matched clip extents and true gaps. Retain farthest-ending coverage selection and overlap-only 80 ms fades.
- Retain overlap-based static loudness gains, whole-clip fallback and final true-peak verification. Worker writes `pending.wav` and result metadata. It never changes the published mix.
- Store commits a successful pending file under a fresh generated mix filename, then atomically replaces set metadata pointing to it. This pointer is the publication boundary. Prior result remains playable through upload/edit/start/failure/recovery. Keep the preceding audio until the next job cleanup to avoid deleting a file before an already-authorized response opens it. Recovery discards temporary job outputs; it never discards the published pointer. A failed metadata publication leaves the prior mix authoritative.
- Dirty state tracks recordings awaiting an automatic update; failed or interrupted updates expose a retry. A single Store timer debounces pending builds for three seconds and dispatches them through the existing single-worker pool. New changes reset that set's pending deadline. Uploads to a running set are blocked, so in-flight snapshots cannot become stale; queued sets accept further uploads. On restart, queued/running jobs resume from cached preparation, at most twice automatically before requiring explicit Retry. Cache versioned audio analysis and feature arrays beside immutable originals. Keep one upload and one worker globally, block edits to a busy set, retain process-group deadlines and inherited flock across parent crashes.

Upload batches use an explicit begin/finish boundary: processing stays held while all selected files are attempted, then exactly one update is queued for successful additions. Single-file uploads queue automatically. Failed files remain named in the UI error; successful originals and the old mix are retained. An abandoned batch settles after 60 seconds without an active upload; an in-flight chunk holds the batch open and has a two-minute body deadline. Reselecting the same files resumes committed offsets after interruption or restart. Only the initiating signed-in uploader can append to or finish their batch.

## Original media and UI
An authorized `/sets/{set_id}/clips/{clip_id}/media` endpoint streams the immutable original through FileResponse with MIME selected from a fixed extension map, inline playback, byte ranges and optional attachment download. It uses the same shared/private set middleware and secure playback cookie as compiled audio. Never expose storage paths or tokens in URLs. Native video is used for MP4/MOV/WEBM, audio for audio extensions; browser codec compatibility varies, so original downloads remain available.

The UI has a set list/create form, set detail with one compiled video player (audio fallback), direct video upload, and original media cards. Preserve published player identity through edits and processing; change its revision only when a replacement publishes. Status is concise. No reference, gain, alignment or diagnostic controls. Retain original removal as a simple per-recording action; inclusion remains an API compatibility operation. Legacy reference cards say “Original only” and cannot be toggled into ordinary contributions.

## Bounds and operations
Maintain 64 recordings per set, 3 GiB/file, 20 sets, two hours per recording, eight aggregate hours per set, ten-minute decoder/measurement deadlines and a four-hour job deadline. Local defaults reserve 16 GiB for originals, 10 GiB for generated work and a 2 GiB physical free floor. R2 originals, unfinished transfers and retained mixes share a hard 8,000,000,000-byte application quota, independent of the 10 GiB local work budget. The original legacy reference may remain longer but is not newly decoded. Single-worker generated storage is bounded. Atomic JSON and volume persistence handle ordinary restarts, not guaranteed power-loss durability.

Hosted image uses `/crowdset/` assets, non-root user, persistent `/data`, 2 CPU/2 GiB cap, one replica and manual deployment. Exact-prefix routing preserves other apps. Browser request-policy errors must be recovered normally, never bypassed. The service was first deployed on 2026-10-16; the capacity/storage extension still requires its own rollout.

## Larger set capacity and recovery

Preserve these algorithms and matching thresholds. Production has a 38 GiB disk with 28 GiB free as observed on 2026-10-18; the 4 GiB host previously exhausted memory during concurrent builds, so keep one build and one processing worker.

- Centralize validated operator settings and expose active upload limits through the authenticated catalog endpoint's `limits` query. Default 64 recordings, 3 GiB/file, 2h/file, 8h/set, 16 GiB originals, 10 GiB generated, 2 GiB physical free floor, 8 MiB chunks, 24h upload expiry, 2h job deadline, 10min media subprocess deadline.
- Introduce a narrow filesystem original-store boundary. New immutable originals live in `originals/<set>/<recording>`, upload parts/manifests in `uploads/<set>/`; legacy original paths remain readable without migration. Working WAV/features and current mix retain the set directory. Optional private R2 and Supabase Storage providers materialize originals into bounded staging and proxies authorized range media responses; it does not change recording IDs. Its private immutable object keys include recording ID and full SHA256. A durable object ledger accounts for uploaded and unpublished revisions; the current and preceding mix generations survive cleanup.
- Reserve declared original bytes across all unfinished sessions. Admission counts originals, parts, reservations and actual generated work, and reserves the unused work quota plus host free floor on the real filesystem. Reject new work before quota/free-space exhaustion. Probe duration using the existing restricted decoder; bound actual decode by the probed duration and reject inconsistent/oversized media. Reserve cumulative expected float WAVs/features and a new worst-case union mix before a job. Enforce actual aggregate duration as decoding completes.
- Persist upload owner, set, file fingerprint, size, committed offset, expiry and completion state in atomic manifests. Every append/finalize checks ownership and batch binding. Verify chunk SHA256, require the expected offset, and make exact retries idempotent. Flush committed bytes before advancing offset; truncate uncommitted tails on restart. Complete via immutable rename and idempotent catalog insertion.
- Persist batch IDs/owner/expiry alongside each set and persist pending job state in existing metadata. Reconstruct timers on startup, retain unfinished resumable sessions, and requeue interrupted jobs at most twice; independent parent/child job deadlines remain coordinated. Preserve inherited directory flock and process-group termination.
- Cache alignment by immutable source ID, anchor ID and analysis version; changing anchor invalidates matches. Add per-recording progress. Keep native media `preload=none` for the catalog's recording cards.
- Preserve all host/origin/owner guards. Local legacy direct PUT uploads retain compatibility; cloud mode rejects old clients with a reload instruction, so all cloud originals use the checked resumable finalizer. No database or production credentials are added.

### Supabase Storage deployment

Configure `CROWDSET_STORAGE_KEY` as a server-only Supabase secret/service-role key and `CROWDSET_STORAGE_BUCKET=crowdset-media`; never prefix the secret with VITE or include it in build arguments. Reuse `CROWDSET_AUTH_URL`. The bucket must be private with an explicit file limit at least `CROWDSET_MAX_FILE_BYTES`, and the project's global upload limit must also permit that size. Startup validates the bucket before opening the catalog. Cloud bytes transfer with TUS in 6 MiB chunks, durable server transfer offsets, immutable keys and size verification. Downloads are streamed with server authorization; no public URLs or credentials reach the browser.

`CROWDSET_ORIGINAL_BYTES` defaults to 80 GiB with cloud storage, 16 GiB otherwise. Both include pending reservations; cloud output publication reserves its bytes before upload. After the new pointer commits, garbage collection retains the current and preceding mix objects and deletes older/unpublished revisions. Failed cleanup retains its ledger reservation and retries with the next job. Local staging and caches remain on `/data`, which still needs independent backup for set ownership, metadata, manifests and job state. Supabase object durability alone does not back up this metadata or provide multi-writer coordination.

As checked on 2026-10-19, Cozy Commons is on Supabase Free (50 MB maximum file size). Enabling 2 GiB cloud uploads requires an approved plan upgrade and global/bucket limit change. Pro starts at $25/month, includes 100 GB storage and 250 GB egress, with usage charges above allowances. No plan, bucket, production credentials or existing originals have been changed by this implementation. Legacy filesystem originals remain readable, so no automatic bulk migration is needed for rollout.


### R2 free-tier deployment (selected provider)

Use a dedicated private Standard-class bucket. Disable public `r2.dev` access, leave custom domains unset, and configure a one-day abort lifecycle for incomplete multipart uploads. Do not enable Infrequent Access, replication, event consumers or other paid features. Inspect account-wide current and month-to-date storage/operation usage before activation; this app cannot limit unrelated clients. R2 has no hard free-tier billing cutoff. Standard includes 10 GB-month, 1 million Class A and 10 million Class B requests monthly, with free direct egress ([official pricing](https://developers.cloudflare.com/r2/pricing/)). Budget alerts do not stop charges ([billing alerts](https://developers.cloudflare.com/billing/manage/budget-alerts/)).

Configure these Coolify **runtime-only** variables:

```text
CROWDSET_STORAGE_PROVIDER=r2
CROWDSET_STORAGE_BUCKET=cozycommons-crowdset
CROWDSET_R2_ACCOUNT_ID=<Cloudflare account ID>
CROWDSET_R2_ACCESS_KEY_ID=<bucket-scoped Object Read & Write access key>
CROWDSET_R2_SECRET_ACCESS_KEY=<secret access key>
CROWDSET_ORIGINAL_BYTES=8000000000
```

Keep credentials out of VITE variables, build arguments, logs and Git. Before enabling the provider on the existing persistent volume, initialize the request budget **once** for the new empty bucket using the new image with provider unset and the R2 variables available:

```bash
python -m crowdset.r2 --initialize-budget
```

Then enable `CROWDSET_STORAGE_PROVIDER=r2` and restart through Coolify. Initialization refuses to overwrite an existing ledger. Back up `/data/r2-requests.sqlite`, `/data/objects/` and `/data/r2-transfers/` alongside the complete metadata volume. Never restore an older request ledger or reset counters to regain allowance; reconcile any recovery against actual account usage first. Switching buckets/accounts requires explicit usage reconciliation, not deletion of the ledger.

Every HTTP attempt consumes a durable SQLite budget before network access: 100,000 Class A and 1,000,000 Class B over the latest 35 UTC days. Missing/corrupt counters, account mismatch or a clock rollback pause requests. Cleanup DELETE/Abort requests are free and remain available for known upload IDs; an interrupted creation must first be reconciled with a budgeted listing. HTTP retries and redirects are disabled. SigV4 credentials are restricted to the configured HTTPS account host. Startup reconciles every remote object and unfinished multipart transfer against the persistent local ledger; unknown objects, uploads or non-Standard storage block startup.

Each original or mix has one immutable key and a full-size reservation before any part transfer. Sequential 8 MiB multipart uploads persist creation intent before the request and the upload ID before sending bytes, resume existing parts after validating their size/MD5, and verify completed size and SHA256 metadata. Lost completion responses are recovered by HEAD. Aborting/deleting must be acknowledged before releasing reservations. Current and previous mixes, pending originals and orphaned transfers all consume the 8 GB cap. Local staging still needs the existing work/free-space quotas. The 3 GiB per-file ceiling also remains enforced. No transcoding or automatic original migration is performed.

Rollout must verify a small authenticated upload, playback and byte-range download against the real bucket, followed by a service restart and replay. Inspect provider usage after the smoke test. Code/mock tests alone do not confirm a live R2 connection or account-level $0 billing.

### Event metadata API (frontend handoff)

`GET /crowdset/sets?limits=true` advertises `event_metadata: true`. `POST /crowdset/sets` still requires `name` (1–120 characters); legacy `{name}` creation remains valid. Structured creation additionally supplies all five top-level fields together: `artist` (1–120), `venue` (1–160), `starts_at`, `ends_at`, and `timezone` (valid IANA zone). Blank strings and partial event objects return 422 without creating a set.

Datetime strings use ISO format with `T`. Native `datetime-local` values without an offset are resolved in `timezone` on the server. Nonexistent or ambiguous daylight-saving wall times return 422; the API accepts an explicit offset to disambiguate. Offset-aware inputs represent their stated instant (including `Z`); timezone remains the event's display zone. End must be strictly later than start. A midnight crossing supplies the next calendar date explicitly. Stored/returned start and end are UTC ISO strings with `+00:00`; artist/venue are trimmed. All five fields persist and appear unchanged in authorized list/detail responses across restart. Old sets may omit every field. Event metadata does not establish clip timing, affect audio alignment, or change permissions.

The frontend can search and surface likely duplicates from this authorized catalog; the server does not claim a duplicate-prevention guarantee. No guessed contributor display names or compiled-video endpoint are added. Existing uploader IDs remain internal identifiers, not display attribution.


## Canonical video publication

`video.py` probes the first decoded audio and moving-video timestamps (excluding attached cover art), then bounds picture coverage using the final packet PTS plus duration from a copy-only, 128 MiB-limited packet scan. Analysis cache version 2 retains their relationship. A separate deterministic visual planner uses all confident ordinary videos, the existing audio union origin, and a single 24 fps global frame grid. It chooses farthest-ending active coverage with stable ID ties and represents gaps explicitly. Audio selection, alignment and fades remain unchanged.

Render segments sequentially to a 1920×1080 square-pixel H.264 canvas with aspect-preserving padding, auto rotation, one encoder thread, 3 Mbps VBV ceiling and a neutral background after early video EOF. Seek using the decoded audio origin rather than assuming container/video zero. Concatenate verified frame counts and mux 96 kbps AAC from the finished WAV into one faststart MP4. Each output has a conservative byte bound; reserve local space for both intermediate segments and final output, plus one materialized original. Existing process-group, worker and subprocess deadlines apply. Failed/restarted work removes only abandoned render/cache copies, preserving immutable originals and published media.

Reserve combined cloud audio/video bytes before either upload. Both private objects must finish before the single durable set metadata replacement commits their shared revision and timelines. The current and preceding manifests/files/objects survive cleanup; uncommitted generations retain their quota reservation until remote cleanup succeeds. Audio and video endpoints honor `v` and serve only current/previous revision pointers with the existing authentication and byte-range path. No public object URL or credential enters the browser.

The video player replaces the audio player only when `video_playable` is true. Its source is revision-pinned, and polling/upload states preserve its identity until successful publication. Audio-only/legacy results continue using the audio player. Event timestamps do not influence rendering.

## YouTube import

POST `/sets/{id}/youtube` validates and canonicalizes only standard YouTube watch, short-link, shorts and live-video URLs to a single 11-character video ID. Existing host/origin/auth/visibility checks apply. Reserve one original upload slot and the maximum file bytes before download, plus bounded temporary disk headroom. Use the existing exclusive worker slot and a child process group with a deadline; no downloader runs inside a request thread. Pin yt-dlp/EJS and provide Node and ffmpeg in the runtime image. Disable playlists, live streams, cookies, user config, remote components, unbounded retries and downloader logging; select at most 1080p, merge to MP4, and bound file/directory bytes and duration. Credentials are not inherited by the downloader.

Download progress is persisted for normal status polling. Final bytes go through the existing resumable upload finalizer (actual audio duration, total duration, SHA256, private R2 publication and automatic processing). Persist import/session identity before launching. A failed or interrupted import preserves the published cut; remove unpublished media through acknowledged storage cleanup before releasing its reservation. Restart marks interrupted imports retryable and cleans their staging files. Completed URL imports are idempotent within a set. Tests cover input restrictions, metadata and byte guards, quota/admission, failure/restart, ownership and successful shared finalization; real YouTube availability remains host-dependent.

Processing telemetry is written atomically to progress.json. Each video segment uses a separate FFmpeg progress file; API reads are bounded to the last 8 KiB and use the last complete report. Frame counts accumulate across segments and gaps. Remaining time is estimated from observed encoding fps and applies only to the video render. Finalization and cloud publication have distinct phases with no invented percentage. The four-hour whole-job deadline accommodates the observed production encoding speed (roughly 0.6x for a 91-minute 1080p source); it does not change the two-CPU, memory, request, disk, or cloud storage caps. Existing jobs retain the deadline captured when they started.

The single-recording fast path requires an uncut, zero-offset 1920×1080 progressive H.264/yuv420p, square-pixel, non-HDR source with zero audio/video origins and a verified contiguous 24 fps packet presentation grid. Allow at most 100 ms of terminal audio padding, preserving the full processed WAV when muxing AAC. Copy video packets into a faststart MP4; do not use the original audio. Older cached analyses re-probe video metadata without invalidating audio preparation. Reserve the larger of the regular rendition bound and original bytes plus 16,000 bytes/second plus 16 MiB; publication still enforces the shared 8 GB quota.

After audio rendering and level validation, compare the finalized WAV checksum with the current published audio cache and compare the complete visual plan with the published visual plan. Reuse the current revision only when both media outputs are unchanged and the published media remains available. Reused results update clip analysis and alignment without new blob reservations, uploads, or revision rotation. Cloud video is streamed from the published object; discard its redundant local rendition while retaining the published audio cache for exact rebuild comparison. Keep local-only media and remote current/previous revisions intact. Worker HTTP storage exceptions preserve their explicit detail. The 10 GiB work and 8 GB R2 limits remain unchanged.

## Official soundtrack composition

Owner-only `PUT /sets/{id}/soundtrack` selects an included clip ID (or null to clear). Workers pin alignment, audio selection and bounds to that clip. Ordinary sets keep the existing planner. The composition planner uses matched videos shorter than the official recording, keeps a chosen friend until its coverage ends, chooses earliest onset/stable ID among overlaps and skips already-started remainders under three seconds. All boundaries use the existing 24 fps grid, clipped to the official duration.

A composition is an in-app edit, not a concatenated MP4. Reuse the official base when its visual plan and final audio checksum match the published base. Otherwise render that base through the existing copy/transcode path. Encode only selected friend intervals to silent H.264/yuv420p MP4s with the existing rotation, padding, bitrate, process and byte bounds. Asset IDs include clip identity, timing and normalizer version. Current and previous revisions can reuse immutable normalized inserts. Reserve every new artifact before cloud publication and commit the manifest only after every upload succeeds; failed publication keeps the old cut. Garbage collection retains shared base objects and inserts referenced by either retained revision. The 8 GB cap and durable request ledger apply unchanged.

The revision-pinned base video supplies the only audio and playback clock. ## Short clip matching
Clips below the existing three-window duration use full-clip normalized correlation against the anchor. Require similarity at least 0.35 and a 0.12 margin over competitors outside ±240 ms; nearby repeated beats still compete. Verify the timing within 160 ms in two disjoint sections for clips below six seconds, or three for longer short clips, each with similarity at least 0.25. Require at least 60 feature frames (about 2.5 seconds of decoded audio), and full anchor coverage. Keep the existing long-clip matcher unchanged. These scores are heuristics, not probabilities. Show concise unmatched reasons. Alignment cache version 2 recomputes previous decisions while retaining the version 2 WAV/feature/analysis preparation caches and original bytes.

Capture metadata version 1 extracts container-level timezone-qualified QuickTime creationdate (preferred) or creation_time, plus camera make/model. Ignore stream/output tags, filesystem/upload dates and YouTube imports. Backfill metadata from originals without rebuilding WAV/features; metadata failure falls back to audio. For hints, require at least two non-anchor global audio matches from the same uploader, camera model and timestamp tag, separated by at least 30 seconds, with inferred set-start times spanning at most four seconds. Search within ±15 seconds of the predicted offset only for ambiguous short clips, preserving the full audio acceptance criteria. Confident global audio wins; inconsistent clocks are ignored. Assisted matches never seed calibration. Cache only independent audio results; recompute hints/assisted results each job so changed peers cannot leave stale decisions.

## Player hover previews and shortcuts

The processing worker prepares cached JPEG storyboards for video sources selected in the visual timeline, including unchanged cuts. The manifest maps source-video time to a sheet/tile; the client resolves source time from the selected segment's offset and the video's audio-relative start. These are approximate interval snapshots, not frame-accurate seeks.

Content identities include source hash, video timing, and generation parameters. Store sheets and manifests on the persistent local volume like clip posters; they count against the 10 GiB working-space cap and add no R2 objects. Preparation has the existing bounded media timeout and is optional: failures leave a playable cut and timestamp-only inspection.
